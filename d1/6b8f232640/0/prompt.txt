## Property verification

**1. Step ordering vs. the single buffer — ✅ correct at every one of the 11 buffer transitions.**

The idiom throughout is `read(b)` → borrow dies on a `Copy` value → `buf_mut()` patches *the same resident block* → `write(b)`. Confirmed at three sites (`alloc_zone:686-695` bitmap, `place_zone:635-645` indirect, `write_inode:726-732` inode) and at the partial-write splice (`do_write:527-555`).

The two places where a block is fetched while another was recently resident:
- `place_zone:623` reads the indirect block; `zone_from_indirect` returns `u32` (`:624`), so the borrow is dead before `alloc_zone` at `:632` replaces the buffer. The explicit re-read at `:635` is correct and necessary.
- `alloc_zone:686` reads a bitmap block; `bitmap_find_free` returns `u32` (`:690`), so `buf_mut()` at `:693` is the *same* block and `bitmap_set` patches the right bytes.

`read_inode` returns an owned `Inode` (`main.rs:771-778`), so step 1 releases the buffer at the `let`. `Chunk` is `Copy`. Nothing is held across a fetch.

**2. Allocation ordering (leak-vs-share) — ✅ correct, and this is the strongest part of the diff.**

`alloc_zone:693-695` sets the bit and **flushes the bitmap block to the device** before `:708` writes the zone and before the number is returned to any caller. The consequence that matters: `place_zone`'s Indirect arm calls `alloc_zone` twice in one request (`:626` indirect block, `:632` data zone), and the second call re-reads the bitmap *from disk* — where the first call's bit is already set. Sharing is impossible by construction. Had the bitmap flush been deferred, those two calls would have returned the same zone.

Every partial-failure path leaks in the safe direction: bit set + `Err` (`:701`, `:708`), or zone allocated + `place_zone`/`do_write` returning before `write_inode` (`:555`, `:564`). No path stores a zone number anywhere before its bit is durable.

**3. Fresh zones zeroed — ✅ both cases, via one code path.**

`alloc_zone:707-708` (`zeroed(); write(zone)`) is on the only path that returns a new zone, so data zones and indirect blocks are covered identically. `place_zone:610-616`'s comment states this correctly. The redundant re-read at `do_write:527` for a partial write into a just-zeroed zone is correct (the buffer holds the bitmap block at that point, so it *must* re-read) — the report's concern #2 is right on both counts.

**4. Inode write-back condition — ✅ correct, including the case the brief warned about.**

Hole-fill in the middle of a file: `place_zone` returns `(zone, true)`, `grow_size` returns the unchanged size, `dirty` stays `true`, `write_inode` runs. ✅

The subtle third case is also right: allocating a data zone into an *existing* indirect block returns `dirty = false` — correct, because the pointer went into the indirect block (already flushed at `:645`) and the inode genuinely did not change.

`Inode::to_le_bytes` (`inode.rs:122-136`) covers all 64 bytes and round-trips every field, so `write_inode` cannot silently zero a field the decoder ignored. I checked this specifically; it's clean.

## Findings

### Important 1 — `zone_ok` has no lower bound, so a corrupt zone pointer lets the write path destroy metadata
`fs/mfs/src/main.rs:595`, `:617`, `:626` (all three call `walk::zone_ok`, defined `fs/mfs/src/walk.rs:225-227` as `zone != 0 &amp;&amp; zone &lt; blocks`).

`alloc_zone` can never return a zone below `first_data_zone` (`:673`, `:697-699`), but a zone number read *off the device* is checked only against `0` and the device size. An inode with `zone[i] == 3`, or `zone[7] == 4`, passes `zone_ok` — and `do_write` will then `blocks.write(3)` over the zone bitmap, or `place_zone:645` will patch and store block 4, which is the inode table. On the read path this same weakness only mis-*reads* a block; on the write path it converts one bad pointer into a destroyed filesystem, and there is no fsck to recover.

Reachability: needs an already-corrupt image, which VFS cannot forge. But `walk.rs:21-30` states the repo's own position — "a corrupt image is not a hypothetical the way it is for a filesystem with an `fsck`" — and every other device-derived value in this crate is defended on exactly that reasoning. The fix is one comparison; `alloc_zone:673` already computes `first_data_zone - 1`. Suggest a `write_zone_ok(zone, layout, blocks)` used at the three sites above (and possibly a note at `read.rs`'s side that the reader deliberately stays looser).

### Important 2 — `buf_mut()` is a hole in the `Blocks` capability, and `do_write`'s doc overclaims what the borrow checker enforces
`fs/mfs/src/main.rs:204-211` (`buf_mut`), `:213-229` (`write`), doc claim at `:470-473`.

The `Blocks` token's guarantee is *aliasing*: you cannot hold one block's bytes while fetching another. It says nothing about buffer *identity*. `Blocks::write(block)` flushes "whatever is resident" to an arbitrary block number, and `buf_mut()` hands out the buffer without stating which block it holds — so `blocks.buf_mut(); …; blocks.write(some_other_block)` compiles and silently writes block A's contents as block B. That is precisely the corruption class the token exists to prevent, and the doc at `:471-473` ("the borrow checker enforces it because every `Blocks` method takes `&amp;mut self`") reads as if it covers this. It does not.

All four current call sites are correct. Three are read-modify-write of the same block. The fourth — `do_write:531` with no preceding read — is correct only because of the three-hop chain I traced above, none of which is asserted at the site: the guard is written `chunk.len &lt; mount.block_size` while `Blocks::write` flushes `MFS_BLOCK_SIZE`. If `read_super:757` were ever relaxed to accept a smaller block size, this line would flush `MFS_BLOCK_SIZE - block_size` bytes of a stale block into the file, with no compile error and no test to catch it.

Not a present bug. But with zero runtime coverage on this code, I'd want either (a) a resident-block field in `Blocks` so `write()` takes no block number (or asserts the one it's given), or at minimum (b) the guard spelled `chunk.len &lt; MFS_BLOCK_SIZE` plus a `const _: () = assert!(FS_MAX_IO &gt;= MFS_BLOCK_SIZE)` in `lib.rs`, and (c) the doc at `:470-473` narrowed to say what it actually guarantees.

### Minor 1 — `grow_size` runs after the data is already on disk
`fs/mfs/src/main.rs:564-567`.

`grow_size` is a pure function of `node.size` (known at `:494`), `req.pos` and `chunk.len` (known at `:504`). Evaluating it at `:564` means its two error cases fire *after* a zone has been allocated, its bitmap bit set, and a block written — and `do_write` then returns the errno without calling `write_inode`, leaking the zone. Hoisting it next to `clamp_write` moves both failures ahead of all device work at no cost. (Unreachable today: `clamp_write` bounds `pos` below ~4.03 MiB, so only `cur &lt; 0` — a corrupt inode — can fire.)

### Minor 2 — leak amplification on retry
`fs/mfs/src/main.rs:555-559`, `:571`.

Report concern #4 notes that a mid-write failure leaks a zone. What it does not note: because the inode is never written back, a **retry of the same write re-allocates** rather than reusing. A client looping on a bad grant leaks 1–2 zones per attempt, and the rootfs has ~250 data zones. Worth a sentence in `do_write`'s doc so the next reader knows it was considered, and worth remembering when Task 5's VFS retry loop lands.

### Minor 3 — no timestamp update
`fs/mfs/src/main.rs:560-571`. `mtime`/`ctime` are never touched; a written file keeps its `mkfs` timestamps. MINIX's MFS sets `IN_UPDATE` here. `Inode::to_le_bytes` round-trips both fields so nothing is *lost* — this is an omission, not corruption — but it's undocumented, so it reads as an oversight rather than a decision.

### Minor 4 — `write_inode`'s missing `zone_ok` rests on an undocumented caller precondition
`fs/mfs/src/main.rs:719-722`, `:726`. The justification ("every caller has already read this same inode through `read_inode`") is true for the one caller that exists and is stated in the doc — good. Blast radius is contained anyway, because `inode_location` (`read.rs:56-70`) bounds the block to `inode_start..inode_start + inode_blocks`. Note only.

### Minor 5 — inconsistent error relay at the pre-read
`fs/mfs/src/main.rs:527-529`. `blocks.read` already returns `EIO`; `if …is_err() { return EIO }` discards and re-synthesises it, unlike the `match … Err(e) =&gt; return e` form used at `:494`, `:504`, `:509`, `:564`. Cosmetic, but the asymmetry invites a reader to wonder whether the mapping was intentional.

### Minor 6 — stale ABI doc, outside this task's files but inside the slice
`kernel-shared/src/callnr.rs:938`: `BDEV_WRITE` still documents "**Answers `EROFS` as of slice 5.7**". Task 2 made it store. Should be corrected before the slice PR — `fs/mfs/src/main.rs:1113` now refers to that behaviour in the past tense while the ABI header still asserts it in the present.
