## 4. How the boot image / load loop distinguishes stubs from real servers and init

The distinction is architectural, not a runtime tag on the stubs — **stubs live in a completely separate path from MXBI servers**:

- **Boot servers + init + worker** are packed into the MXBI archive by build.rs and loaded by the archive-driven loop in `userland_bootstrap` (lines 153-165):
  ```rust
  let image = crate::boot_image::BootImage::get();
  for (nr, elf) in image.iter() {
      if nr.get() &lt; 0 {          // EXEC_ONLY_PROC_NR sentinel (= -1): `worker`
          continue;              // packed for SYS_EXEC name resolution, no proc slot
      }
      load_boot_server(nr, elf);
  }
  ```
  The **only** discriminator inside the MXBI loop is `nr.get() &lt; 0`, which skips the exec-only `worker` module (`com::EXEC_ONLY_PROC_NR = -1`, defined `kernel-shared/src/com.rs:104`). Init is NOT special-cased here — it is loaded as an ordinary boot server (proc_nr 10); its "PID 1 / ordinary user" nature is expressed only in its priv slot (see below) and in PM's mproc seeding.
- `boot_image/mod.rs` (`/Users/kevinbarnard/src/minixrs/kernel/src/boot_image/mod.rs`): `BootImage::get()` (lines 53-77) validates the header/records; `iter()` (lines 92-98) yields `(ProcNr, &amp;[u8])`; `proc_and_elf` (lines 147-153) decodes the proc_nr/offset/len. `boot_image/elf.rs` does the PT_LOAD parsing into an AddrSpace.
- **Stubs A-D** are then built by four explicit `build_stub` calls (lines 171-220) — entirely outside the archive loop, from the linked `_user_stub_*` blobs.
- **Proc/priv-slot seeding difference:** boot servers get their proc + dedicated priv slots pre-populated by `proc::init()` → `init_boot_image()` (`kernel/src/proc/table.rs:448-468`) from the static `IMAGE` array (`table.rs:140`, `N_IMAGE = NR_TASKS + NR_BOOT_PROCS = 16`, line 137). Those slots boot blocked on `RTS_NO_PRIV` (`table.rs:515`), and `load_boot_server` clears it after loading the ELF (`userland.rs:373` `p.rts_flags.store(0, …)`). Init is special-cased *inside* `init_boot_image` (`table.rs:454-463`): it is pointed at the shared `USER_PRIV_ID` (20) rather than a dedicated server priv slot. Stubs, by contrast, have **no `IMAGE` entry** — their proc slots are filled entirely by `populate_stub_slot` and their priv slots (16-19) by `install_stub_privs`, at userland-bootstrap time.

So a `boot-stubs=off` build would remove: the `user_stub.S` source from build.rs, the extern block, the VA/priv-id constants, the four `build_stub` calls + enqueues + priv installs + `print_addrspace_summary`, while leaving the MXBI loop and `load_boot_server`/`load_exec_image`/`STUB_SPSR_EL0` intact.

## Summary of the consistency contract to preserve

`NR_STUB_PROCS` (in `kernel-shared::com`) is the single source of truth. It feeds:
1. `com.rs` compile-time asserts 95-96 (reference `STUB_A/D_PROC_NR`) — will need gating if the stub proc-number constants are `#[cfg]`'d out.
2. PM `mproc.rs::FORK_POOL_BASE = NR_BOOT_PROCS + NR_STUB_PROCS` (line 41) — automatically shifts the fork pool down when stubs are gone; PM's seeding loop `.take(NR_STUB_PROCS)` (line 150) already degrades cleanly to zero.
3. Kernel `userland.rs` stub install/enqueue (lines 173-684) — the other half that must be gated in lockstep so the kernel doesn't create EL0 stub processes that PM's mproc no longer knows about.
4. Host tests in `com.rs` (158-172) and `mproc.rs` (423-587) that hard-code 4 stubs / slots 11 &amp; 14 / expected fork pid 15.
