## Issues

### Critical (Must Fix)

**1. The band's own ABI doc still says every CDEV driver short-writes past `CDEV_MAX_IO` — which this branch made false, and the book contradicts itself about it.**

- `kernel-shared/src/callnr.rs:1098-1103` (`CDEV_WRITE` doc): *"A request longer than [`CDEV_MAX_IO`] is a **short write, not a failure**: the driver moves the first `CDEV_MAX_IO` bytes and reports that count, and the client re-sends with `offset` advanced."*
- `kernel-shared/src/callnr.rs:1176-1178` (`CDEV_MAX_IO` doc): *"Largest byte count a character driver moves in one `CDEV_WRITE`. A longer request is short-written."*
- `book/src/drivers/overview.md:195-201`, listed as one of the **"Five properties of that table are load-bearing"**.

The memory driver, as of this branch, answers the whole count for any `len` — Z4, deliberately, and `drivers/memory/src/cdev.rs:13-19` says so. So `CDEV_MAX_IO` is *not* the largest byte count a character driver moves, and a driver does *not* move only the first 256 bytes. The book states this as a band property on line 195 and then states the opposite on line 391 (*"Nothing is clamped: `CDEV_MAX_IO` protects TTY's stack staging buffer, and there is no staging here"*) — a self-contradiction 190 lines apart, in the same chapter, introduced by this branch.

Why it matters: this is the ABI's source of truth. The half that is genuinely load-bearing is the *client* obligation ("a short write is legal, so loop"); the half that is now false is the *driver* guarantee. A future driver author reading `CDEV_MAX_IO`'s doc will believe clamping is required.

Fix: reword all three to the client-side contract — "a driver **may** answer short, so the client re-sends with `offset` advanced (that is what lets a driver stage through a fixed buffer with no allocator); TTY clamps to `CDEV_MAX_IO` for exactly that reason, the memory driver stages nothing and never clamps." Keep the count at "Five properties". `CLAUDE.md:355`'s 5.3 bullet carries the same sentence but is immediately followed by the new 5.11 bullet correcting it, so it can stay as a historical record.
