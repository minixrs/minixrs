### Findings

- **fs/mfs/src/main.rs:555 — a zone is allocated and bitmap-marked before the copy that can fail, so any unprivileged process can permanently exhaust the root filesystem's free zones.** `rw::validate` in VFS only checks the buffer *range* (`user_range_ok`), not that it is mapped, so `write(file_fd, in_range_but_unmapped_va, 4096)` reaches MFS with a well-formed magic grant. `place_zone` then sets the bitmap bit, zeroes and stores the zone, and only afterwards does `sys_safecopy(SAFECOPY_FROM, …)` return `EFAULT`; the inode is never written back, so the zone is orphaned with its bit set and a retry allocates a *fresh* one. The shipped 256-block image has roughly 185 free zones, so ~185 such calls fill it and every later write — including a legitimate one — answers `ENOSPC` for the rest of the boot. The docstring does acknowledge the leak ("a client looping on a bad grant … one or two zones per attempt"), but frames it as incidental rather than as reachable from any process holding a file descriptor. I could not find a reorder that fixes it under the one-block-buffer constraint (the allocator needs the buffer for the bitmap block, so it must run before the splice), and rollback is genuinely unsafe in the indirect arm because `place_zone` has already made the indirect block durable — so this may be an accepted cost, but it should be an explicit one, and it argues for a per-request or per-client allocation cap before 5.10b adds `O_CREAT`.

- **tools/mkfs-mfs/src/verify.rs:404 — `the_image_leaves_room_for_the_scratch_file_to_grow` cannot detect the failure it documents.** It measures `sample()`, a test fixture whose `/bin/hello` is 9 blocks and which has no `/etc/pattern` and no `/etc/scratch` — that leaves ~235 free zones against a threshold of `free &gt; 8`. The shipped image is built from a different manifest in `kernel/build.rs` (`/bin/hello` is 49 blocks in the musl flavour, plus a 40 KiB `/etc/pattern`), and nothing in this test is a function of it. A future growth of the real image's contents — the most likely cause, and the one outside this repo's control, since `hello`'s size depends on the toolchain flavour — would leave this test green and surface only as `fs.write FAIL short` in the QEMU boot. Either build the real manifest here or assert on `ROOTFS_IMAGE_BLOCKS` minus a computed static footprint.

- **kernel-shared/src/rootfs.rs:328 — the seam assertion is `&gt;=` where the property it states needs `&gt;`.** `assert_eq!(ROOTFS_SCRATCH_LEN.min(7 * BDEV_BLOCK_SIZE), 7 * BDEV_BLOCK_SIZE)` holds at exactly `7 * BDEV_BLOCK_SIZE` (28672), which is precisely the length at which the file fits the seven direct zones and the single-indirect *allocation* arm — the thing the comment says this test exists to keep on a boot marker — becomes unreachable. Nothing is broken today (the `const _` at rootfs.rs:161 uses a strict `&gt;`, and the neighbouring `assert_eq!(ROOTFS_SCRATCH_LEN, 32 * 1024)` pins the value), but per the house idiom the boundary form should be `assert_eq!(LEN.min(7 * BDEV_BLOCK_SIZE + 1), 7 * BDEV_BLOCK_SIZE + 1)`.
