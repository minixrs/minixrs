## Review of PR #52 — exec-from-FS (slice 5.9)

### Findings

- `kernel/build.rs:203` — **medium**: the "load-bearing" DS publish-before-retrieve chain comment still reads `ds &lt; tty &lt; memory &lt; mfs &lt; vfs`, but slice 5.9 made PM a client of VFS via `vfs_endpoint()`'s `DS_RETRIEVE`. - `kernel/src/arch/aarch64/userland.rs:511` — **low**: the `SERVER_STACK_VA` stack-page map folds *every* `MapError` into `ENOMEM`, which is exactly the stance this slice set out to end. Since exec-from-FS the ELF is an input, so an image whose own segments cover `0x0020_0000` now returns `MapError::AlreadyMapped` → `ENOMEM` ("the machine is out of frames") for what is really `ENOEXEC` ("this is not an image this kernel will run") — the same class of file `init`'s `not-elf` probe exists to distinguish. Cleanup and rollback were already correct; only the errno was wrong. **Fixed**: routed through the new `elf_errno(ElfError::Map(e))`, so only a genuine allocator failure stays `ENOMEM`.
- `userland/init/src/main.rs:562` — **low**: the `relative` probe's doc bullet opens with "`EINVAL`:" and then spends three lines correcting itself to `ENOENT` (which is what the code asserts). A reader skimming for the expected errno gets the wrong one. **Fixed**: bullet now leads with "**`ENOENT`, not `EINVAL`**".
- `tests/qemu-boot.expected:268` — **low**: the comment above the five C markers still says `hello` is "exec'd out of the boot archive", which this PR made false by dropping the module — and it sits directly under the new `src=grant` block that explains the opposite. - `kernel/src/boot_image/elf.rs:132` — **low**, *not fixed*: `scan_brand_chunked` stages only the first `MAX_NOTE_BYTES` (256) of each `PT_NOTE`, while `kernel/build.rs`'s pack-time gate still calls the unbounded `brand::scan_brand`. Not reachable with this repo's `user.ld`/`hello.ld` rule (dedicated 28-byte `PT_NOTE`), but the SDK flavour has zero CI coverage and does not use `hello.ld`, so it is the one place the divergence could show up.
